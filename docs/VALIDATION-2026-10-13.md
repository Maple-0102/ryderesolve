# Judge 优化与队友 Advocate 实测 · 2026-10-13

## 已完成

- 通用 Judge 提示词去掉具体案件的答案提示，按本次案卷和审计判断；仍是规则辅助的系统。
- 规则来源、源路径、团队检查约定及版本哈希进入计算结果和页面。
- 新增非事实请求类型，不让程序请求或注入指令冒充有证据支持的事件。
- 明确责任条件编号、全额/部分退款标签和记录金额边界；未放宽证据检查。
- 加入可配置推理档位，测试 LOW；默认仍为提供商配置，未自动修改本地账号配置。
- 模拟测试包15题（9开发、6尚未用真实模型运行的留出候选），模型输入与评分答案分开。
- 一次补材料重跑接口、来源说明、前后快照追踪及页面记录；离线流程已验证。
- 队友原始 Advocate 模块接入现有 ADC 传输、两轮对等回应和当前 Evidence 快照。

## 程序验证

集成测试124项通过；队友 Advocate 原包15项通过。原包27个文件逐字节哈希未改变。
两个核心 schema 与 Evidence 模块相同。未生成、发布或分享 API Key。

## Judge 开发题

四次完整开发评估的严格匹配分别为3/9、3/9、5/9、8/9，各自提示词哈希与原始失败输出均保留。
最后一次完整评估5个应复核题全部通过，3个保留收费题全部通过，顺序对照两题均正确。
部分退款题因误标refund_full被拒绝；进一步明确金额标签后专项复测1/1通过。
**不能把不同提示版本拼成最终9/9。当前金额修正版本尚未重新跑完整9题。**
该集合曾被用于调提示词，不是独立泛化评测；全额退款业务场景未覆盖。
9题开发与6题留出候选仅来自两个种子家族，不是15个独立业务样本或官方标准答案。
没有证明现实运营准确率、公平性或全面提示注入防御。

## 真实三方联调

官方DISP-002：真实Evidence模块 → 双方开场 → 双方回应 → 真实Judge。
模式：Advocate=teammate_google_vertex，Judge=google_vertex；同一Google Cloud模型返回完成标记STOP。
4次Advocate + 1次Judge，共5次真实请求，检查20条论点，validation_errors=[]。
最终escalate，refund_amount=null；核心缺口是缺少权威等待起算规则和早到等待是否计入。
该次实际耗时约80.7秒，记录到43816 tokens。
页面 `outputs/team-live-2026-10-13/ryde-evaluation.html` 为静态运行记录，打开不调用模型。

## 质量观察与下一步

司机开场有较强的“到达后满足8分钟”表述，需要更明确地标成条件性论点，不能自己确定政策起算点。
GPS采样支持采样点的位置/速度，不应表达成全程连续停留得到证明；需继续人工抽查这类措辞。
Judge本例保留计时缺口并拒绝强制收费，一例成功并不代表全部论证语义正确。
下一步优先确认官方政策缺口、实测合成路线案例的真实Advocate联调、固定配置后跑6题留出候选，随后准备演示和提交材料。
补材料 API 尚未接入运营资料检索；没有新增第二个LLM审查Agent，也未部署腾讯ADP云应用。
